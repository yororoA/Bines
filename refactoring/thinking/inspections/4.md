  - **[status_trim_node.py:69](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/status_trim_node.py#L69)** 和 **[dynamic_agent_node.py:87](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/dynamic_agent_node.py#L87)** 永远用 `get_cancel_event()`（全局）。这意味着传入的 per-thread cancel_event 实际上在这两个节点是无效的，**取消事件可能串扰到无关线程**。

### 2.2 取消不真正生效（debounce 路径）
- [napcat_server/napcat_connection.py:96-103](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/napcat_server/napcat_connection.py#L96-L103) 在 `_handle_debounce` 里只调用 `cancel_thread(thread_id)` + `old_task.cancel()` + `await old_task`。
  - `old_task` 来自 `loop.run_in_executor`（即 ThreadPoolExecutor 上的 `Workflow.invoke`）。`Future.cancel()` 在线程已启动的情况下不会真正终止。
  - 即使 cancel_event 被 set，**节点内部只有进入节点体那一刻才会检测**（`performer_node.py:239`、`context_builder_node.py:130`），正在执行的 LLM 同步调用不会被中断。
  - 接着 `await old_task` 在事件循环里**阻塞**等待线程池任务结束，期间整个 NapCat 事件循环无法处理新消息，违反非阻塞原则。

### 2.3 全局 ContextManager 并发相互污染
- [workflow/context_manager.py:68-71](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/context_manager.py#L68-L71) 暴露的是**进程级单例** `_context_manager`。`ThreadPoolExecutor(max_workers=4)`（[workflow/workflow.py:31](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/workflow.py#L31)）允许多个 `Workflow.invoke` 并行：
  1. `_get_ctx` 拿到的 `inner dict` 引用是在 `with self._lock` 内返回的（仅保证 dict 引用存在），但 `set/append_to_list/update/reset` 操作 `inner dict` 时**没有锁**。两个 workflow 同时写同一个 thread_id 的 inner dict 不会竞争，但不同 thread_id 之间共享同一个 `_contexts` dict，pop/insert 之间的原子性靠锁。
  2. 真正的并发污染：`_local = threading.local()` 与 `Workflow.invoke` 提交到 ThreadPoolExecutor 的 worker 线程一一对应（worker 会复用），但 `set_active_thread(thread_id)` 写入的 `thread_id` 在 worker 上是会被跨任务覆盖的——任务 A 进入 worker 时调 `set_active_thread(A)`，A 阻塞后 worker 接手任务 B 并改写 `_local.thread_id = B`，A 再恢复时 `_get_active_thread()` 读到的就是 B。**因此所有节点在用 `ctx.update / ctx.get` 时实际可能错位访问到别人的 context**。
  3. `reset()` 仅在调用时清空对应 thread_id，但**老任务还在跑**时清理会导致 KeyError 或更糟——`inner dict` 引用被 pop 后还在被旧任务使用。

## 3. 线程冲突

### 3.1 ThreadPoolExecutor 内的 ContextManager 单例
- **位置**：[workflow/context_manager.py:68-71](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/context_manager.py#L68-L71) + [workflow/workflow.py:31](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/workflow.py#L31) + [tools/napcat_tools/common_msgs/cmsg_tools.py:40-41](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/tools/napcat_tools/common_msgs/cmsg_tools.py#L40-L41)
- **冲突**：
  1. 多个 `Workflow.invoke` 并发跑在 ThreadPoolExecutor 4 个 worker 上，所有 worker 共享 `_context_manager` 单例；
  2. `_local.thread_id` 是 `threading.local()`——`ThreadPoolExecutor` 复用 worker，**先到的任务 A 写入 `_local.thread_id = "QQ_group_1"`，任务 A 阻塞到 LLM 期间，worker 接手任务 B 并改写 `_local.thread_id = "QQ_group_2"`，A 恢复后 `_get_active_thread()` 返回的是 `"QQ_group_2"`**；
  3. `set_active_thread()` 在每个 `_run` 中调用（[workflow.py:171-175](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/workflow.py#L171-L175)），但节点函数可能在 worker 上同步执行，调用栈跨 await 时同样会被覆盖。
- **后果**：节点 A 写 `persona_snapshot`，节点 B 紧接着读 `persona_snapshot` 读到的是 B 的内容；`send_msg` 工具在 worker 线程中执行时 `ctx.append_to_list("reply_texts", [reply_text])` 会写到错位 thread_id 的 context。

### 3.2 `_PerformerAgent` 单例 + `_PerformerLock` 串行化
- **位置**：[workflow/nodes/performer_node.py:19-21](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/performer_node.py#L19-L21)、[performer_node.py:253-264](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/performer_node.py#L253-L264)、[performer_node.py:288-289](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/performer_node.py#L288-L289)
- **冲突**：用全局锁保护 `_PerformerAgent.run`；多个并发 workflow 会在 `_PerformerLock` 上互相等待。同时 `ctx.set("target_type"/"target_id"/...)` 发生在 PerformerNode 之前的 `_build_context` 中（[performer_node.py:102-106](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/performer_node.py#L102-L106)），但因为串行化，即使错位写入，下一个任务开始前会再覆盖——**所以这个案例下污染概率比 3.1 小**，但仍然是隐性串行瓶颈 + 仍然依赖 3.1 中的 ContextManager。

### 3.3 `_pending_requests` / `_seen_message_ids` / `_debounce_timers` / `_running_tasks` 在异步代码中用 `threading.Lock`
- **位置**：[napcat_server/napcat_connection.py:58-66](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/napcat_server/napcat_connection.py#L58-L66) + 全文 `_task_lock`
- **冲突**：
  1. `_task_lock = threading.Lock()` 在纯 asyncio 代码里使用。在单事件循环线程里**等价于无锁**，不会立即出错（CPython 单线程 asyncio 内 bytecode 切换点不会发生），但违反惯例，且未来若引入 `loop.run_in_executor` 把这段代码搬到线程里会立即失效。
  2. `_handle_debounce` 锁内 `pop` 后 `await` 旧任务，**锁已释放**；两个新消息依次进入时，会出现：消息 1 pop timer A → cancel A → 锁外 await；消息 2 抢锁 pop timer A（已为 None，OK），append content。逻辑上看似一致，但 `_pending_buffers.setdefault(...)` 与 `_debounce_callback` 中再 `pop` 之间存在窗口，**可能出现 buffer 内容被合并到新的 debounce 计时器而旧计时器已清空**——导致消息被静默丢失。
  3. `_listen` 里的 `_pending_requests` 也是裸 dict：`_listen` 协程 + `call_api` 协程共享，**在单线程 asyncio 内 OK，但若 call_api 之后业务侧在另一个线程里塞新 request 就会丢**。

### 3.4 `_seen_message_ids` 跨重启/重启后状态丢失
- [napcat_server/napcat_connection.py:61-74](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/napcat_server/napcat_connection.py#L61-L74) OrderedDict 限 1000 条仅在内存。重启后 NapCat 会重发部分消息，可能误判"duplicate"或漏判"duplicate"。**不是线程冲突但是状态冲突**。

### 3.5 `global_client.napcat_client` 的多步初始化
- [main.py:71-79](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/main.py#L71-L79) `gc.napcat_client = napcat_client` 在主线程中执行，但 [tools/napcat_tools/common_msgs/base.py:10-21](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/tools/napcat_tools/common_msgs/base.py#L10-L21) `_run_async` 会在 worker 线程里读 `get_client()`。`napcat_client` 是模块级变量，**写入未加锁 / 未发布**——Python GIL 保证单赋值原子性，但"先于关系"（happens-before）要靠 `gc.napcat_client = ...` 这条语句与 worker 线程的 `get_client()` 之间有同步点，否则 worker 仍可能读到 `None`。生产中一般不会出问题，但严格意义上**有 data race**。
