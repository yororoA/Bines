## 2. 逻辑/架构问题

### 2.1 `PerformerNode` 全局锁导致并发瓶颈（严重架构问题）

**[performer_node.py](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/nodes/performer_node.py#L19-L20)** 使用了模块级全局锁 `_PerformerLock`，在 `PerformerNode` 函数的第 253 行和第 288 行分别持有该锁来构建和运行 agent：

```python
_PerformerLock = threading.Lock()   # 全局锁

with _PerformerLock:                 # 第 253 行 - 构建 agent 时加锁
    ...
with _PerformerLock:                 # 第 288 行 - 运行 agent 时加锁
    feedback_raw = _PerformerAgent.run(task_input)
```

这意味着**整个系统中同时只能有 1 个 Performer 在执行**。任何并发的用户消息都会被这个全局锁串行化。

### 2.2 线程池并发能力与全局锁的矛盾

**[workflow.py](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/workflow.py#L31)** 创建了 `ThreadPoolExecutor(max_workers=4, ...)`，但由于上述 `_PerformerLock` 的存在，**4 个 worker 同时只能有 1 个实际干活**，其余 3 个都会被阻塞在锁上。线程池的并发能力被完全抵消。

### 2.3 `ContextManager` 的 TOCTOU 竞态条件

**[context_manager.py](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/workflow/context_manager.py#L28-L33)** `_get_ctx` 方法在锁内创建/返回 dict 引用，但调用方（`set`、`update`、`append_to_list`）在**锁外**对该 dict 进行修改操作。

其中 `append_to_list`（第 52-57 行）存在典型的 read-modify-write 竞态：
```python
def append_to_list(self, key, items, thread_id=None):
    ctx = self._get_ctx(thread_id)   # 获得锁 → 返回 ctx → 释放锁
    existing = ctx.get(key, [])       # 读取（无锁保护）
    ...
    ctx[key] = existing + items       # 写入（无锁保护）
```
如果两个线程以相同 `thread_id` 同时调用此方法，后写入的会覆盖先写入的，导致数据丢失。虽然当前设计上每个 `thread_id` 绑定单个线程（通过 `threading.local()`），但如果未来任何代码绕过了 `set_active_thread` 直接传 `thread_id`，就会出问题。

### 2.4 `PersonaCache.get()` 返回可变引用

**[persona_state.py](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/memory/persona_state.py#L58-L60)** `get()` 方法在锁内返回 `self._cached` 的 dict **引用**：
```python
def get(self) -> dict[str, Any] | None:
    with self._lock:
        return self._cached
```
调用方拿到的是可变 dict 的引用，可以在外部修改缓存内容，破坏缓存一致性。应返回 `dict(self._cached)` 副本。

## 3. 线程冲突

### 3.1 `_get_ctx` 锁与外部修改的分离（已述详见 2.3）

`ContextManager` 的锁只保护了 `_contexts` 字典的键插入/删除，但不保护值的修改，这是典型的线程安全问题。

### 3.2 `NapCatClient._task_lock` 的使用一致性

**[napcat_connection.py](file:///e:/Desktop/desktop/work/coding/bines/refactoring/thinking/napcat_server/napcat_connection.py#L66)** `_task_lock` 是 `threading.Lock()`，但在 `_handle_debounce`（第 87-109 行）中：
- 第 87-88 行：加锁读取并 pop `_debounce_timers` 和 `_running_tasks`
- 第 105-109 行：加锁写入 `_pending_buffers` 和赋值 `_debounce_timers[thread_id]`

而在 `_debounce_callback`（第 111-145 行）中：
- 第 117-119 行：加锁 pop `_debounce_timers` 和 `_pending_buffers`
- 第 135-136 行：加锁写入 `_running_tasks[thread_id]`
- 第 143-144 行：加锁 pop `_running_tasks`

问题在于：`_handle_debounce` 中两次加锁（第 87 行和第 105 行）之间有 cancelling/waiting 的 await 操作（第 90-103 行），在此期间锁已释放。如果同一 `thread_id` 的 `_handle_debounce` 被快速连续调用，可能导致对旧 task/timer 的 cancel 操作与 `_debounce_callback` 中的 pop 操作产生竞争。不过由于这些都在同一个 asyncio 事件循环中运行，实际并发风险较低。
