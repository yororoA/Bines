### 已经完成的优化

- 普通会话的固定人设与规则在前，历史随后，动态状态和本轮资料靠后。
- 历史保留一个 30 条的起始段，允许追加到 40 条后再推进；每次读取最新原文，修订和撤回仍生效。

- 建联使用紧凑证据编号，默认每页最多 6 个候选；已有正负决策缓存。原持久化每日预算及额度核销现已移除。

## 两条上下文路径的差别

### 聊天与实际行动路径

当前主顺序可以概括为：

`工具规则 / schema → 固定人格与行为规则 → 分段历史 → 场景 → 状态、生命与画像 → 回忆 → 时钟与本轮口吻 → 当前输入 → 后续回执 / 观察`

`prompt_builder` 在可用材料预算内按历史 40%、画像 15%、召回 30%、状态 10%、跨渠道 5% 分配，并允许未用额度在栏目间借用。实际请求发送前，`bound_request` 再计入工具声明和当前输入等开销。

这一路仍有精简空间，但供应商已经复用了大部分输入：自主行动为 82.23%，QQ 为 72.76%。优先大幅删减它们的历史，收益与行为影响的比例不如修复自主评估入口。

### 自主意愿与情绪评估路径

`common/proactive.py::_complete()` 的顺序却是：

`本次评估规则 → 精确时钟 → 整个 data 对象的 JSON`

而 `appraise_history()` 的 JSON 又先放 `previous_emotion`、兴趣和近期行动结果，再放记忆。即使只把时钟移动，这些靠前的动态字段也会继续破坏后面大块材料的前缀复用。[评估入口](file:///Users/bytedance/Bines/common/proactive.py#L577-L638)

QQ 与桌面调度器都将 `recent`、`memories`、`profile`、`bridge`、`state` 等对象直接放进材料。记忆对象含完整内容、原文 evidence、来源家族、节点摘要、检索分数、`context_id` 等字段；普通聊天中已有的呈现裁剪和去重没有在这里应用。`recent_outcomes` 同时存在于材料内和评估外层，构成明确重复。[QQ 调度材料](file:///Users/bytedance/Bines/chatBot/proactive.py#L277-L324)、[桌面调度材料](file:///Users/bytedance/Bines/thingking/src/bored_detector.py#L113-L145)、[记忆 DTO 字段](file:///Users/bytedance/Bines/thingking/src/memory/service.py#L78-L95)

这一入口仍经过 `complete_text → bound_request`，但通用预算器不理解一个巨大 JSON 内各个字段的重要性，并且不会静默截断最新 user 消息。因此它没有得到普通会话那样的细分预算效果。样本中的平均输入为 **28,782 token/次**，比实际自主行动的平均 19,227 token/次还大。

### 预算单位需要先校准

现有 55 个带诊断的实际回合均使用 `utf8_byte_upper_bound`。日志里名为 `assembled_tokens`、`schema_units` 的数值在这批样本中实际是 UTF-8 字节上界加封装预留，不能直接当作供应商 token。

例如 QQ 请求的工具 schema 固定计数为 **17,850 个上界单位**，不能说成“工具声明每次消耗 17,850 token”。同样，`BINES_CONTEXT_MAX_TOKENS=65536` 是整理软目标，不是已验证的模型硬窗口。[计数与预算](file:///Users/bytedance/Bines/common/context_budget.py#L21-L110)

可配置与当前服务模型匹配的本地 tokenizer，再与供应商回执校准。但不能保留数值 65,536 不动就宣称节省：将字节上界换成真实 token 后，同一个数字可能反而放宽输入量。需要同时重新标定软目标、schema 和输出预留。

## 推荐实施顺序

### 第一阶段：保持决策机会和工具能力，重组重复输入

| 优先级 | 改动 | 实施约束 |
| --- | --- | --- |
| P0 | 为自主评估建立专用材料投影；情绪评估与行动意愿共用同一组来源材料 | 保留人格、兴趣、未完成目标、事实、原始结果及当前权限；不直接把整个记忆 DTO 交给模型 |
| P0 | 按变化频率重排评估请求 | 固定规则和能力说明在前；稳定历史与证据居中；当前情绪、意愿、生命状态、权限与精确时钟在后 |
| P0 | 消除确定重复字段 | `recent_outcomes` 只出现一次；同一来源正文与 evidence 的相同片段只传一次，保留两者的来源映射 |
| P0 | 统一可重复的序列化 | 字典键序稳定，字段值不变时呈现不变；不按内容重排真实消息的时间顺序 |
| P1 | 分清业务资料与内部元数据 | `context_id`、哈希、评分分解、来源依赖图留在服务端；模型保留可引用来源、发生时间、有效期、纠错、结论及必要原文 |
| P1 | 将评估账本细分 | 分开记录 emotion appraisal、intent decision、activity reflection，便于判定是哪类判断耗费大 |

建议请求布局：

```text
固定人格 / 安全与行为约束
固定能力摘要，按版本生成
稳定的近期历史段
去重后的记忆正文与必要证据
当前评估任务及输出结构
本次变化：情绪、意愿、状态、权限、时间、最新输入
```

情绪评估与行动意愿若能共享前四部分，就有机会复用共同前缀；任务差异仍明确保留。指令保持原有可信层级，用户、网页和记忆始终标记为资料。最终布局仍需按接入端的实际序列化验证，不能凭本地字符串相同就承诺命中。

首版投影宜先做完整保真的去重和元数据移出，再考虑更短的证据卡。不能直接把自主评估改成只看几个摘要：当前 `_complete()` 没有模型选用工具的循环，单纯给它 `read_memory_source` 的 ID 并不能让它自动展开。需要展开时，必须补齐取材路径，或在首版保留原有决策所需文本。

缓存对象是已经计算过的输入前缀。**不缓存“现在是否行动”的答案**，也不沿用过期权限和情绪。休息、联系限制、未完成目标及精确时间继续逐次刷新。

### 第二阶段：降低建联重复工作，并保持巩固可用

当前建联路径为：

`节点新建/修订 → associate 任务 → 检索最多 12 个候选 → 同源排除 → 6 个候选一页 → 模型判断 → 来源/纠错版本核验 → 写入关系及决策缓存`

证据编号已替代模型逐字复述引用；默认首轮原节点取 420 字、候选取 280 字，恢复时扩展材料。因此“把建联 prompt 变短”“加负缓存”已经部分完成。[排队入口](file:///Users/bytedance/Bines/thingking/src/memory/associations.py#L244-L300)、[材料准备](file:///Users/bytedance/Bines/thingking/src/memory/service.py#L952-L1015)、[紧凑协议](file:///Users/bytedance/Bines/thingking/src/memory/association_plan.py#L76-L132)

样本中 100 次建联调用发生于 11 月 2 日 00:00:03—00:01:29，输入加输出为 **144,119 token**。调用数先达到默认 100 次上限，低于 300,000 token 的日预算。快照另有 **250 个 associate 任务因日额度延期**。

`RetentionStore.freeze()` 会等待本批来源上仍在 pending/running 状态的建联任务。它不会被所有历史回填阻塞，但相关来源的额度延期仍可能传导到摘要或日记。快照当时没有待执行的摘要任务，故这是修改前明确的代码依赖风险，不能声称已经测到了摘要延迟时长。[冻结依赖](file:///Users/bytedance/Bines/thingking/src/memory/retention.py#L27-L42)

建议按以下次序处理：

1. **修正决策缓存身份。** 当前 key 虽含节点版本，也包含页内 `t1/t2` 和 evidence 编号，候选换位置可能造成额外未命中。应使用稳定节点/证据摘要计算缓存键，仅在提交模型时生成页内别名；保留策略版本、模型版本、作用域和纠错依赖。
2. **保留严格的内容版本去重。** 相同节点版本、相同证据与相同相关约束的判断可直接复用。不能仅按关键词、时间间隔或向量相似度把两段独立经历当成一次判断。
3. **按因果完整性处理反向候选。** 若复用 A→B 与 B→A 的判断，必须转换关系方向及证据身份。当前全库缓存 6,265 条，对应 6,231 个有序节点对、6,176 个无序节点对；仅靠交换节点顺序去重的机会有限，不应预期大幅降耗。
4. **调度优先级照顾正在巩固的来源。** 优先处理活跃回合和摘要依赖，历史回填随后；调用额度已按用户要求移除。
5. **为暂未完成的建联设计可恢复巩固。** 可先生成派生摘要并继续保护全部相关原文，将按图权重收冷的决定延后；关系完成后再自动处理保护与收冷。不得把“未判断”记成“无关系”，也不得提前丢弃原文。

最后一项改变巩固状态机，应与建联、恢复和来源修订一起验证后上线，不属于一次简单参数调整。

样本窗口内最后写入/刷新的 340 条缓存决策中，222 条为空关系，118 条有关系，空关系占 65.29%。这说明弱候选值得优化，但**不能推出“65% 的调用可以安全跳过”**：它们是候选对而非调用，而且判断是否无关系本身依赖证据。

长期可将廉价检索线索与有证据的语义关系分开管理：实体、事件来源等确定信息负责候选发现；因果、冲突、支持关系仍需明确证据。若引入模型判断门槛，应保留候选和自动补判，并通过召回质量回放证明不会损失远距离关联。关闭 `BINES_MEMORY_ASSOCIATIONS` 会连带影响图检索，不适合作为保持能力的默认降本动作。

### 第三阶段：进一步减少经历摘要与工具续轮的重复内容

经历摘要在窗口内 116 次调用，对应 260 个来源的摘要任务完成，已有合批效果。两者不能简单解读为固定批大小，也不能再按“6 条合批节省 6 倍”计算额外收益。

独立经历内容不同，公共前缀天然较短，0.25% 命中率不一定代表缓存机制错误。应优先减少输入和输出里的重复语义：

- 同一活动的目标、来源页面、公共背景在请求内只出现一次；每条来源保留自己的操作、结果、新发现和时间。
- 相同工具回执、自动网页观察和活动 checkpoint 的重复内容以来源引用关联；保留真实的重复动作及事件次数。
- 模型仍逐来源输出摘要，服务端继续验证来源齐全、无重复、修订版本有效，不能把其他来源的成功结果写到本来源。
- 在不损失来源映射的前提下，评估短别名替代长 `source_ref`，回写时由服务端恢复真实编号。

不建议为了节省摘要调用扩大到跨用户合批，也不建议无限增加等待时间。摘要和日记表达变化可能影响后续记忆质量，应单独回放评估。

工具续轮还有两个可见空间。其一，每个新的秒级时钟目前会再次附上整段时钟解释；可保持首份解释完整，后续仅追加明确的最新采样值。其二，网页变化会追加完整 `website_observations`，这些 system 消息不属于现有工具结果节选规则，旧观察会继续累积。[时钟追加](file:///Users/bytedance/Bines/common/clock.py#L28-L50)、[网页观察追加](file:///Users/bytedance/Bines/common/website_perception.py#L59-L89)

网页可采用“一份本轮基线 + 有来源的增量观察”，但必须保留页面身份、采样时间、视频片段范围、加载状态和真实变化。新页面、刷新、元素编号变化应重建基线；历史工具结果和未确认写操作仍保留，不能因压缩造成操作重放。单纯缓存“同 URL 的描述”会损失实时性，不符合本次约束。

## 不影响现有行动的验收边界

本次可以把“能力与关键事实不缩水”作为工程约束；模型随机生成的具体措辞和每次选择，不能仅凭重排输入就保证逐字、逐步一致。

| 验收对象 | 必须保持 | 衡量方式 |
| --- | --- | --- |
| 行动能力 | 同身份下可用工具、参数、发现入口及运行时权限一致 | 对比实际提交 schema；执行前权限仍重检 |
| 自主性 | 原评估触发条件、活动续接、休息调节与长期目标保留 | 回放 continue/pause/finish、planning_only 与联系限制场景 |
| 当前材料 | 本轮输入、任务约束、最新状态与时钟不被静默裁剪 | 对比最终发送请求中的必要字段 |
| 事实与来源 | 有效期、纠错、反证、原话与来源身份保留 | 检查最终 prompt 的证据覆盖，不能只看检索命中 |
| 操作连续性 | 已执行回执、未确认状态、工具 call/result 配对保留 | 连续工具轮与中断恢复回放，禁止重放副作用 |
| 隔离 | owner、普通私聊和群聊的权限/记忆边界一致 | 同一内容在不同身份下的访问回归 |
| 后台整理 | 不因调用额度停工、不把未决当否定；自动恢复无需人工逐条处理 | 旧额度迁移、进程中断、来源修订与恢复用例 |

优先复用现有验证入口：`test_model_cache.py`、`test_frontend_memory_budget.py`、`test_memory_efficiency.py`、`test_retrieval_prompt_quality.py`、`test_activity_request_budget.py`，以及 `verification/context_budget_integration.py`、`verification/memory_retrieval_eval.py`。最初分析阶段仅检查实现与覆盖范围；后续额度移除验证另记于文末，未发起真实模型调用。

新增验证的重点应是自主评估入口：时钟、情绪变化时前面的证据是否仍然稳定；元数据投影后关键事实是否完整；QQ 与桌面两条调度路径是否一致。只测 `build_conversation_messages()` 不足以覆盖此次最大消耗点。

建议先对正常业务请求做无额外模型调用的材料影子对比，记录栏目大小、前缀一致长度、重复来源量和必要字段缺失数。校验通过后，再小范围切换组装方式，按相同任务类别和每个实际回合比较 token、延迟、召回覆盖与任务结果。不能用多发预热请求或统一削弱输出能力来制造好看的命中率。
