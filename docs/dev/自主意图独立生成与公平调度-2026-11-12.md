# 自主意图独立生成与公平调度

新版已部署到本机 Docker，8 个服务健康。运行镜像源码摘要与当前工作区一致，真实 QQ 连接及 worker 探针通过。

## 设计修正

此前意图生成与执行共用可用性门控：当前自主任务执行中、有待执行任务或活动在等待，都可能使新意图无法产生。模型选择暂缓后，全局下一次取舍时间又会阻止其他方向继续考虑。

现在将目标生成、目标排队与实际执行分开：

- 独立生成时钟 `next_intention_at`，默认每 60 秒允许一次评估；模型调用前保存时钟，调用完成后重新限速。
- 正在执行自主任务时仍可生成新的目标，进入持久队列。工具与消息继续按当前会话串行执行。
- 队列最多保存 8 个新目标，按类别及具体目标去重；同一兴趣中的不同目标可以并存。独立目标 6 小时后过期，联系目标遇到新的用户消息会失效。
- 到期旧活动与新目标按批次交替获得执行机会，执行时重新检查身份、最新用户消息和联系权限。
- 需要人工验证或回执不确定的活动独立保留为暂停目标；其他目标可以继续。恢复活动先重新观察，不重放旧动作。

等待有明确作用范围：

| 模型选择 | 调度行为 |
| --- | --- |
| `review`，默认 | 本轮没有新目标；继续按正常节奏考虑，已有活动仍可执行 |
| `contact` | 只暂缓联系主人，重复等待不延长原截止时间 |
| `all` | 明确选择整体休息，暂时暂停生成与执行；新消息或真实活动结果可触发重新考虑 |
| 活动自身延迟 | 保存该活动的继续时间，其他目标仍可产生和执行 |

睡眠、休息、主人暂停、用户消息优先及连接断开仍按各自语义生效。内部评估不会要求模型为了填满队列强行选择任务。

相关实现：`common/proactive.py`、`common/intent_queue.py`、`chatBot/proactive.py`、`thingking/src/bored_detector.py`。新增字段随原自主状态一并存入 Redis，支持重启恢复。

## 截图中的异常

建联流程在事实核验前校验紧凑证据编号及完整候选覆盖；失败后只给一次纠正机会，反馈逐候选可用的双方编号。服务端继续校验证据来源及任务领取版本。

线上重放进一步确认任务 13123 的具体错误：模型引用了 6 个真实编号，接口每条关系最多接受 4 个；旧提示未说明数量限制，校验又将数量超限统一报告成“编号无效”。现已在首轮及纠正提示中明确每条引用 2 到 4 条、通常双方各选一条，并区分“证据数量无效”与“证据编号无效”。证据数量上限及来源校验保持严格。

HTTP 客户端断开时，网关捕获连接关闭和超时，保留原处理结果与操作回执，避免成功处理后再次发送 503。该行为通过真实断开连接的隔离用例验证。

任务 13123 在首次部署时已因旧校验错误进入失败状态。通过带任务版本、错误类型及作用域校验的 RPC 恢复一次，由新 worker 自动继续处理。恢复后的模型答案仍超过证据数量上限，严格校验拒绝写入，随后定位并修复了提示和报错问题。最终版本部署后，原任务沿上次失败的退避时间自动恢复，现已完成：status=done、attempts=13、未决候选=0。领取次数包含证据展开与分页，不能直接当成失败次数。

观察期间 Memory Server 曾退出并自动重启，导致该容器内的查询进程以 137 退出。观察改为从网关容器只读查询共享数据库后完成，最终确认 8 个服务均健康。
