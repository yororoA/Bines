# Bines 记忆架构与关联网络改造分析

分析日期：2026-10-24。本文已收敛为确定的架构方案，首版关联计权、使用反馈、关联召回和保留策略已实现。第 1–6 节保留改造前的架构证据，第 8–9 节记录实现、后续优化与验证范围。自动冷却默认关闭，尚未验证真实模型建联收益或真实 QQ 登录运行效果。

## 0. 确定方案

采用“分层记忆 + 按理由关联 + 查询时激活 + 后台巩固”。沿用 SQLite 主库、混合检索、Memory Server 与 Worker，在其上增加可解释的关联层和生命周期管理。

- 原始回合、工具经历、摘要、事实与日记均能映射为图节点；真实原文和工具回执保持稳定，派生表达独立版本化。
- 关联理由由模型根据真实材料提出和维护；服务端控制作用域、来源校验、去重、版本与事务。
- 同一记忆在不同理由上的长期召回与引用强度独立保存；每次查询根据问题激活相关理由，在候选与上下文预算内竞争。
- 新建联触发受影响链全部成员的权重视图更新，按关系质量和独立证据计算；重复关系、链成员数量和循环不直接制造强化。
- 只有真正送入模型的资料与有效引用回执进入使用反馈；检索候选、摘要处理和日记改写不算新的独立引用。
- 摘要与日记开始时冻结来源、图水位及保留评分；全量生成成功后执行原始回合最多 Top3、摘要最多 Top1 的直接召回保护。
- 保护排序使用“最强有效理由上的召回强度”，长期强度已包含内容先验、关联置信度和真实使用影响；先去掉重复来源，允许无关联的重要原文参与冷启动排名。
- 其余来源转为冷证据，并降低图中的活跃系数；源数据仍供追溯。冷却不触发撤回，也不缩小日记来源清单。
- 每个 scope 的已巩固热层初始预算为 512 个原始回合、256 条摘要；本轮保护名单以后仍参与全局重评。待摘要数据与运行任务的来源不参与预算冷却。
- 先接入节点、关联与反馈，随后接入查询激活，最后启用 TopK 与全局冷却；使用同一真实语料做消融评测。

以上额度与下文参数是首版工程配置，不是已经证明最优的评测结果。第 7 节定义具体实现约定，后续章节保留现有架构证据和设计依据。

## 1. 现有架构及与需求的差异

Bines 的主要记忆实现位于 `thingking/src/memory/`。Memory Server 管理 SQLite 主数据，Memory Worker 领取状态更新、聊天摘要、经历摘要和日记任务；Chroma 与全文检索键是可以重建的派生索引。QQ 通过网关同步消息，桌面主流程也调用 MemoryService 构造上下文。旧的 `layered_memory.py`、`rag_memory.py` 是兼容接口，不能仅依据它们判断当前系统能力。

| 层次 | 当前保存方式 | 当前行为 | 与目标的差异 |
|---|---|---|---|
| 原始对话 | `messages` | 写入消息，摘要完成后设置 `episode_id` | 没有每轮原始记忆节点、关联链权重或 Top3 保护标记 |
| 对话摘要 | `memories.kind=episode` | 保存摘要、标签、重要性及来源消息 ID | 没有按建联理由关联其他摘要或原始记忆 |
| 长期事实 | `memories.kind=semantic`、`fact_versions` | 提取人物事实，维护单值事实的有效期 | 事实版本关系已有；语义关联与版本关系需要区别处理 |
| 日记 | `memories.kind=diary` | 基于当天摘要生成，来源改变时更新 | 写日记后并不淘汰当天摘要，也没有 Top1 保留机制 |
| 证据 | `retrieval_keys`、来源元数据 | 原文分块，沿来源 ID 回溯真实消息与工具回执 | 来源关系是证据链，不是按关联理由强化的联想链 |
| 召回 | BM25、向量、RRF、主题覆盖、可选 CrossEncoder | 限定 scope 后生成候选并重排 | 没有关联网络扩展、召回反馈或引用反馈 |
| 当前状态 | `state`、`state_history`、生命连续性账本 | 版本化状态及真实事件记录 | 适合复用作为上下文，不能混同记忆链权重 |

### 1.1 当前摘要不会物理删除原文

`complete_summary()` 生成 episode 与 semantic 记忆后，把该批消息的 `episode_id` 写好，以表示已摘要。`EvidenceStore._active()` 将这些已摘要消息排除出直接索引，但证据解析使用允许已摘要消息的读取路径，因此仍能从摘要找到原始发言。最近工作窗口的读取也不以 `episode_id` 判断是否保留。

这意味着原文的“入库”“已摘要”“可直接召回”“能作为证据读取”已经存在不同语义，但没有独立、完整的状态模型。你的 Top3 规则可以利用这种证据保留基础，将部分原文继续放在直接召回层。

## 2. 类脑对应与工程模型

该方向适合定义为“受联想记忆与巩固启发的分层记忆网络”。原始回合快速记录，相关经历建立可解释联系，召回时沿关联激活，后台摘要与日记提供更稳定的表达，同时留下重要的原始证据。

语义扩散激活理论可以作为“相关线索激活其他记忆”的概念参考。A-MEM 直接研究了新增记忆时寻找相关历史、建立链接及更新历史记忆的上下文属性。HippoRAG 使用知识图谱与 Personalized PageRank 组织关联检索。这些工作说明相关机制已有工程先例，但它们不直接验证 Bines 的 Top3/Top1 规则，也不证明该规则等价于生物脑的记忆机制。

来源：[Collins 与 Loftus：A Spreading-Activation Theory of Semantic Processing](https://faculty.sites.uci.edu/eloftus/files/2024/08/CollinsLoftus_PsychReview_75.pdf)、[A-MEM 原论文](https://arxiv.org/abs/2502.12110)、[HippoRAG 原论文](https://arxiv.org/abs/2405.14831)。这三份材料讨论不同机制，不能当作对某一个具体保留算法的三次独立验证。

### 2.1 “关联链”建议成为有理由的成员集合

每条链由稳定理由与适用范围定义，例如某人的特定偏好、某个约定的进展、同一个事件的因果解释。一个节点可以属于多条链。底层可用“理由节点 + 成员关系 + 有证据的关联边”表示：一条成员关系保存该记忆在该理由上的召回权重与引用权重，边保存具体是哪两条记忆、依据哪段证据建立了关系。

这种结构允许 a 同时属于多个关联集合，也能记录后续 b、c、d 对这些集合的影响。关联链无需是按时间排好的单一路径，不应枚举图中所有简单路径；否则分叉与循环会让链的数量急剧增长。

仅有“都提到音乐”“都包含情绪词”不足以认定强关联。链的理由应包含必要的人物、对象、关系和时间限定，模型可以建议新理由、复用或拆分已有理由，服务端维护稳定 ID。模糊理由也可以保留为低置信度候选，避免被用作强支持。

“相似”“共同事件”“因果”“支持”“矛盾”“来源于摘要”需要区分。矛盾记忆可连接，但不能沿“支持”方向相互加强；事实的新旧版本仍由现有时态层判断。摘要来源关系另外记录，不将摘要和原文视作互相独立的新证据。

### 2.2 需要增加的实体

以下为建议结构，不是当前数据库中的表。

| 实体 | 主要字段或关系 | 作用 |
|---|---|---|
| `association_nodes` | scope、source_type、source_ref、source_revision、message_ids 或 memory_id | 将完整回合、摘要、日记映射为稳定图节点 |
| `association_chains` | scope、reason_key、reason_text、revision | 记录链的关联理由与版本 |
| `chain_memberships` | chain_id、node_id、recall_strength、citation_strength、status | 独立记录每个节点在每条链上的权重 |
| `association_edges` | chain_id、两个节点、relation_type、confidence、evidence_refs、event_id | 解释成员之间为什么关联及支持方向 |
| `memory_usage_events` | turn_id、节点、链、事件类型、实际来源 ID、event_id | 区分呈现、实际引用、纠正、生成摘要等事件 |
| `consolidation_snapshots` | job_id、来源与内容哈希、图水位、权重快照、保护名单、策略版本 | 固定摘要或日记开始时的决策依据 |
| 生命周期/巩固记录 | consolidated_into、retrieval_status、retention_reason、冷却因子 | 将已摘要、热召回、冷证据与撤回分开 |

完整回合节点需要可信的 turn_id 或明确的消息集合。现有 `record_turn()` 能知道一次提交的用户与助手消息，但网关逐条同步与工具经历还需要携带轮次来源。旧数据只能对可确定的回合进行组合，不能凭相邻行补造关系。

现阶段可以继续使用 SQLite，并为 `(scope, chain_id)`、节点成员关系和使用事件去重建立索引。是否以后引入独立图数据库，应由真实数据量、链大小及遍历延迟决定；当前设计并不要求更换主存储。

## 3. 权重、竞争及建联更新

### 3.1 召回与引用应分别计权

对记忆 m 在理由链 c 上保存：

```text
recall_strength(m, c)    该理由下被召回的长期强度
citation_strength(m, c)  该理由下作为回答依据的长期强度
association_confidence  具体关系的证据置信度
```

它们与本次查询的临时相关度不是同一个量。候选命中、实际放入模型上下文、回答确实引用、用户确认或纠正，也不是同一种使用事件。

新建联可以调整整条链成员的召回强度与“适合作为依据”的引用强度，但不能伪造已经发生的引用次数。实际引用次数只由有效引用回执增加。模型从本轮真实可见的来源中标注使用 ID，服务端校验；它不能随意指定旧记忆 ID 给自己加分。

现有 `search_memory()` 返回内容与证据，但没有完整返回稳定的命中 ID、链 ID；提示词也没有实际引用回执协议。因此引用权重闭环还需要接入工具返回、提示词和轮次完成记录，不能仅靠数据库计数推断。

代码依据：[当前记忆工具](file:///Users/bytedance/Bines/tools/memory_tool.py#L10-L35)、[当前召回提示块](file:///Users/bytedance/Bines/thingking/src/prompt_builder.py#L202-L254)、[召回操作只作审计的现有处理](file:///Users/bytedance/Bines/thingking/src/memory/service.py#L142-L151)。

### 3.2 长期权重独立，查询激活竞争

最终采用不同理由独立保存长期强度的机制。同一记忆可以同时在“人物偏好”“事件因果”“约定进展”等方面重要；一方面得到新支持，不应无依据地降低另一个方面的长期价值。

成员的召回与引用强度使用统一标定函数，避免不同链各自归一化导致不可比较：

```text
W_recall(m,c) = sigmoid(z_recall(m,c))
W_citation(m,c) = sigmoid(z_citation(m,c))
```

z 根据有效关联证据、真实使用、纠正、时间与重复度更新。新证据仍能改变该链其他成员的权重，因为成员相对作用、证据独立性与关系质量可能变化。

竞争发生在本次召回。查询匹配关联理由后，在统一候选与上下文预算内分配激活；其结果是本轮临时状态，不覆盖长期强度。最终排序以 RRF 融合直接相关度与图激活排名，在来源去重后使用有界的真实使用记录处理接近的候选。

这种设计保留有限注意力的竞争，同时避免长期零和预算对多方面重要的记忆形成惩罚。它也避免只有一条关联链的记忆因归一化份额为 1 就天然获得最高价值。

### 3.3 建联后更新全链的正确含义

新增记忆进入一条链后，应重算该链所有成员的评分，但不必把所有成员统一加同一分数。统一加分不改变成员排名；链越大越强的规则也会让重复闲聊压过关键但少见的事件。

建议一次建联事件只产生一次有界的证据贡献。贡献按关联置信度、支持类型、证据独立性和重复度分配，再结合真实召回与引用记录更新强度。全链更新可通过链版本和统一计算逻辑完成，权重缓存应能重建。

若采用链上扩散，可使用行归一化的支持矩阵、衰减和固定计算边界。循环遍历不得把同一证据再次记为新增支持，传播也不应自动写回原始事实正文。需要解释“为什么权重变了”时，应能从链与事件追溯，而不是让模型重写所有旧记忆。

长期强度更新与本次查询激活分开：查询可以让某条链临时活跃；仅被搜索到不必永久强化。实际使用才记录反馈，并对一次轮次多次读取同一来源去重。

### 3.4 入库顺序与一致性

当前网关按消息时间与 ID 同步，任务也有去重键、重试与租约。这提供了入库基础，但并没有“该批记忆的建联全部完成”的序列屏障。

建议 Memory Server 分配单调的入库事件序号。Worker 基于有限候选判断关联，提交时校验新旧节点版本；模型调用发生在事务外。服务端确认关联后，以短事务提交边、成员变化、使用事件与图版本。

摘要开始前，应确保本批来源及此前应参与排名的建联事件达到就绪水位，然后在短事务中冻结来源、权重和 TopK。不能让唯一 Worker 先领取摘要任务并等待排在其后的建联任务，否则会产生调度互等；应通过任务依赖或就绪条件避免。

生成过程中后来入库的记忆可以继续更新图，但不更改已冻结的本轮保护名单。提交时仍要重新检查来源是否撤回、内容是否变更。撤回与证据失效优先于任何保护规则。

## 4. 原始记忆 Top3 与摘要 Top1

### 4.1 完整保留算法

定义 t₀ 为任务实际开始、材料与图水位就绪后创建决策快照的时刻，而不是任务入队时刻或生成完成时刻。对该批每个原始回合计算：

```text
S(m, t₀) = max[c ∈ chains(m)] W_recall(m, c, t₀)
protected_raw = TopK(该批原始回合, S, k=3)
```

该核心评分保留“每条记忆取其权重最高的一条链，再在本批排序”。引用反馈、内容先验和关联置信度参与长期召回强度的更新，不将所有链相加，以免链越多越占优势。

实际选择先去掉相同 source_ref、来源集合相同且正文等价的重复节点，最多保留三个不同原始回合。没有有效关联链的回合以统一内容先验作为后备分数，避免无关系的重要原文必然被淘汰。同分依次比较不可替代的原文信息、入库序号和稳定 ID。批次不足三条时保留全部有效且不同源的回合。选择规则写入策略版本。

摘要仍读取整批来源。生成和有效性检查成功后，在一个事务里：

1. 保存整批摘要与准确来源集合。
2. 标记所有来源已摘要，包括 Top3。
3. 将 Top3 继续置为可直接召回的原始记忆。
4. 将其余来源置为冷证据，并按策略减弱所有链上的活跃权重。
5. 记录保护原因、快照和任务完成状态。

索引更新可以在事务后执行并由现有 reconcile 恢复。摘要失败或返回无效内容时，不执行冷却和淘汰。任务重试使用同一来源、策略及权重快照；来源撤回或内容变更后，应废弃该快照并重新建立任务依据。

### 4.2 用户示例的结果

```text
开始摘要时：
S(a)=w₁，S(b)=w₂，S(c)=w₃，S(d)=w₄
w₃ > w₄ > w₁ > w₂

摘要来源：a、b、c、d 全部
继续直接召回：c、d、a
转入冷证据并弱化各链活跃权重：b
```

c、d、a 也必须标记已摘要。如果为了保留它们而不设置巩固完成状态，当前待摘要判断会再次选中它们，还可能持续阻止当天日记生成。

### 4.3 日记对摘要的 Top1

写日记时，对本次日记全部摘要来源采用相同快照规则：

```text
protected_episode = TopK(本次日记的摘要来源, S, k=1)
日记输入 = 本次全部有效摘要
日记成功后 = Top1 摘要继续直接召回，其余摘要转入冷证据
```

当前日记仅对 owner scope 的已结束记忆日生成，不应在本次改造中默认扩展到所有 QQ scope。冷却来源摘要也不能调用现有 `delete_memory()`：它执行时态撤回及索引删除，可能使依赖该来源的事实不可见；记忆巩固与用户删除应是不同动作。

需要保持三份不同记录：日记全部来源清单、日记开始时的保护快照、来源当前的热冷状态。当前 `_diary_episodes()` 和 `_episode_signature()` 以活跃 episode 集合计算日记是否需要重写。若冷却后直接缩小这个集合，日记会被判为来源已变，可能重复生成或只根据 Top1 重写。

日记更新应基于全部仍有效的来源与内容哈希，来源转冷本身不触发重写。新摘要补入、来源正文修改或撤回才改变日记证据签名。一次日记修订可在新任务开始时重新选择 Top1，但必须从该日完整有效来源集合评估。

代码依据：[日记来源签名与调度](file:///Users/bytedance/Bines/thingking/src/memory/service.py#L561-L607)、[日记提交校验](file:///Users/bytedance/Bines/thingking/src/memory/service.py#L871-L906)、[删除的时态处理](file:///Users/bytedance/Bines/thingking/src/memory/service.py#L1025-L1042)。

### 4.4 冷记忆保留原文的作用

用户允许未保护的原始记忆退出所有链，或大幅降低所有链权重。建议初版采用冷证据与降权路径：普通召回跳过这些节点，来源解析仍可读取，有新独立证据时通过明确的唤醒事件重新参与关联。

永久删除原文会使摘要错误失去核对依据，还可能破坏日记、事实、工具经历的来源追溯。保留冷证据意味着本方案主要压缩活跃召回面，不能声称它已经节省等比例磁盘空间。真正的原文存储压缩需要另行定义归档、压缩或删除政策。

撤回、删除和失效证据始终不属于可唤醒的冷记忆。它们必须清理关联边、使用来源与检索结果；关联不能成为恢复已撤回信息的通道。

## 5. 召回接入与主要约束

### 5.1 关联网络应参与候选生成和最终排序

建议流程为“当前混合检索获得种子 → 根据问题选择关联理由 → 沿有效边补充候选 → 以问题相关度、链内强度和真实使用证据重排 → 去重并解析来源”。只在原有候选上加链权重，仍然无法找回与问题词面不同、但关联关系明确的记忆。

概念上的最终排序可以写为：

```text
rank(m, q) =
    calibrated_direct_relevance(m, q)
    + bounded_chain_activation(m, q)
    + bounded_usage_prior(m, q)
    - redundancy_penalty(m)
```

这是设计表达，不是经过标定的生产公式。RRF、CrossEncoder 与长期权重的量纲不同，不能直接随意相加。尤其现有 CrossEncoder 会覆盖 `score`，关联分数必须在明确的最终融合位置应用，避免前面加权后又被覆盖。

图传播先限定可信 scope，再取邻居、计算成员数和评分。即使最后过滤了私密节点，也不能先用 owner 网络为群聊候选评分，否则可能通过排序和统计暴露跨 scope 信息。现有独立 scope、时态有效期与撤回逻辑应覆盖图的每条读取路径。

### 5.2 原始 Top3 还需要进入自动上下文

目前 `build_context()` 的自动记忆召回只指定 episode、excerpt 和 diary；主要依靠最近工作窗口看到原始消息。即使给保护原文保留了索引，仍需调整候选种类或使用统一原始回合视图，才能让它们参与更远期的自动召回。

提示词也要同步适配。当前 `_memory_recall_block()` 默认输出摘要，原始证据只在询问原话或保留摘录时输出。如果增加 message 候选却不改展示条件，它可能已命中但没有实际进入模型上下文。应按问题选择有界原文片段，注明说话者与时间，避免把旧对话完整重放为本轮回答范例。

同一事实的原文、摘要、日记是不同表达层，不是三份独立支持。应依据来源家族去重，按问题需要选择表达层，再附所需证据；否则它们会占满上下文并通过互相引用持续加权。

### 5.3 需要约束的增长与反馈

| 问题 | 原因 | 建议 |
|---|---|---|
| 关联越多越强 | 将链成员数量直接当重要性 | 按独立证据、关系质量及重复度计权，做有界或度数校正 |
| 热点自我强化 | 召回导致加分，加分导致再次召回 | 区分候选与真实使用，限制单轮增益，保留探索与衰减 |
| 事实被反复改写 | 让每次建联修改旧原文 | 原始证据不可变，派生描述可版本化 |
| 少见事件难保留 | 无关联或低使用次数 | 定义冷启动与新颖性依据，评测关键但稀少的记忆 |
| 链太宽或太长 | 模糊理由不断吸收新内容 | 限定理由语义，允许拆分，限制在线遍历与传播 |
| TopK 永久积累 | 每批保留三条，每日保留一条 | 另行定义全局热记忆预算或后续冷却规则 |

按批次 Top3、按日记 Top1 能控制每次巩固保留数量，但热记忆总数仍随批次增加。因此采用全局重评，旧的受保护记忆以后也可能变冷；“本轮保护”定义为本次巩固不淘汰，而非永久保留在热层。

最终方案采用全局预算：每个 scope 默认最多保留 512 个已摘要原始回合和 256 条已巩固摘要作为热节点，维护时按最新评分重评，超额转冷。Top3/Top1 是本次巩固的保护名单，不是永久豁免。预算只处理已经巩固且不在运行任务中的节点；新记录、待摘要原文、待写日记摘要和正在生成任务的来源不因预算被提前冷却。日记与事实作为独立视图保留，并受查询候选及上下文预算限制。

## 6. 接入范围与验证方法

### 6.1 建议改造顺序

1. **状态与节点层**：统一原始回合节点，加入关联理由、成员关系、生命周期状态及事件去重；保留现有消息、摘要和来源数据。
2. **入库建联**：新增关联任务，复用混合召回获取有限候选，由模型提出有证据的关系，服务端校验并更新受影响权重。
3. **真实使用反馈**：补充稳定来源 ID、上下文呈现记录与引用回执，形成可审计的召回/引用权重。
4. **关联召回**：增加受 scope 与时间约束的图候选扩展，并在最终重排、提示词呈现及来源去重处接入。
5. **TopK 巩固**：实现开始时快照、原始 Top3、摘要 Top1，以及完整日记来源签名。完成真实语料回放验证后启用冷却。
6. **历史回建与评测**：对现有记忆增量建联，保留不确定的旧来源状态；用真实标注问题比较效果和成本。

### 6.2 必须验证的行为

- 新记忆影响先入库记忆的关联权重，摘要使用开始时的排名，而非入库时或完成时的排名。
- a、b、c、d 全部参与摘要；给定 `w₃>w₄>w₁>w₂` 时保护 c、d、a；b 的所有链进入约定的弱化状态。
- 保护原文仍然标记已摘要，不重复入队，也不阻塞日记。
- 摘要或日记失败、超时、重试不会提前冷却来源或重复强化权重。

- 新来源、正文变更或撤回使旧生成结果失效，保护快照不能覆盖撤回。
- 不同理由的长期强度独立更新，本次查询的激活竞争不污染长期数据；并列、无关联、重复来源、少于 K 条等边界可复现。
- 全局预算只冷却已巩固节点，运行任务和未完成来源不被淘汰；本轮 TopK 保护与后续全局重评分别可追溯。
- 自环、重复事件和摘要—原文—日记循环不制造额外独立支持。
- QQ 群与非 owner 私聊的图扩展、权重统计、引用回执均不使用 owner 私密来源。
- 无向量模型时，词面种子与已有图关系仍可运行；异步索引恢复不改变生命周期决策。

## 7. 实现约定与首版参数

### 7.1 模型与程序的职责

模型负责从限定材料中识别有意义的关系，提供关联理由、类型、置信度和来源片段；可以复用、拆分或修订理由。原始回合的内容先验也由模型结合重要性、独特信息和后续约定给出。程序不硬编码具体兴趣主题，也不因共享一个词就自动建立强关系。

服务端负责真实性与作用域校验、来源版本、事件幂等、任务就绪水位、权重计算与存储。置信度只是模型提出的信号，不能直接当成经过校准的事实概率。边的来源不在当前授权材料中、来源已撤回或版本已经变化时，拒绝提交。

引用反馈使用轮次内的稳定来源 ID 和回答片段，验证引用来源本轮确实可见、回答片段确实存在；精确引用还验证原文片段。改写引用可以记录为有界的报告使用，服务端校验来源可见性不能证明其语义推理一定正确，这部分效果由忠实度评测检查。助手自评“回答成功”不产生额外奖励。

### 7.2 新模块与数据位置

新增 `memory/associations.py` 管理理由、边和成员权重视图；`memory/usage.py` 管理使用事件；`memory/retention.py` 管理冷却、保护名单和快照。服务统一挂载这些模块，新增 `associate` 任务及提交接口，沿用现有 Worker 租约与失败重试。

图表、权重、使用事件和生命周期标记存放 SQLite 独立表，不写进正文 metadata。权重变化不触发正文嵌入；新增或修改正文、理由文本时才更新对应内容索引。SQLite 仍是唯一事实源，Chroma 和全文键可重建。

节点状态分别保存：是否完成巩固、热/冷召回状态、来源是否撤回。事实时态版本继续由现有 TemporalStore 管理。用明确的来源关系连接原文—摘要—事实—日记，语义关系独立存储；来源关系不参与独立支持数的累加。

### 7.3 全链更新与传播

一次关联提交增加受影响链的 revision，并使全部成员的派生评分缓存失效。链的最新权重视图按该版本计算，摘要快照和查询不得读取旧版缓存。全链更新采用版本失效与按需重算，避免每次写入逐条重写所有旧正文；这只改变计算方式，不缩小该事件的影响范围。

长期支持按独立来源聚合，重复边和同源摘要不能反复增加贡献；召回及引用事件按轮次、节点、理由和事件类型去重。每轮同一种反馈对同一来源最多计一次。长期强度采用有界更新，未使用本身不被记为“证据错误”；明确纠正影响证据适用性，时态过期交给事实有效期处理。

在线传播仅用于本轮查询激活，使用支持方向、置信度、行归一化和步数衰减。矛盾关系提供对照候选，不按支持路径传播。长期更新与在线传播不互相递归写回，从结构上避免循环自行累积分数。

### 7.4 首版默认配置

| 配置 | 初始值 | 含义 |
|---|---|---|
| `association_candidates` | 20 | 每个新增完整节点供模型判断的历史候选上限 |
| `retrieval_candidates` | 40 | 复用现有默认种子/最终候选规模 |
| `graph_max_hops` | 2 | 每次查询最多扩展两跳，避免宽链扩散 |
| `graph_candidate_limit` | 40 | 图扩展去重后的候选上限 |
| `retrieval_rrf_constant` | 60 | 沿用现有排名融合常数 |
| `raw_protect_k` | 3 | 每批摘要最多保护三个不同来源的原始回合 |
| `episode_protect_k` | 1 | 每次日记最多保护一条来源摘要 |
| `raw_hot_budget` | 512 / scope | 已巩固原始回合的热层预算 |
| `episode_hot_budget` | 256 / scope | 已巩固摘要的热层预算 |
| `cold_activation_factor` | 0.1 | 冷节点图激活的衰减系数；原文证据追溯不受此系数限制 |

这些参数用于限制计算和活跃面，不代表研究证明的最优配置。关系数量与具体理由不由固定主题表控制。候选上限也意味着模型只判断本轮提供的候选，不会宣称扫描了所有历史；后台可按新线索补建关系。

最终上下文继续使用现有工作窗口、召回条数与提示块预算，并对原文、摘要、日记按来源家族去重。冷节点通常退出直接种子索引；强关联可以在衰减后把它补入候选，真实使用回执再触发重新评估是否进入热层。证据撤回节点永不通过这一路径唤醒。

### 7.5 巩固与恢复的确定行为

完整节点入库并登记关联任务 → 关联就绪 → 创建摘要材料和评分快照 → 模型全量生成 → 来源版本复核 → 短事务提交摘要、全量巩固标记、TopK 及冷却 → 异步索引恢复。

关联任务沿用现有最大重试次数。达到上限仍无法建联时，记录未完成关联状态，摘要使用已提交关系及内容先验冻结评分，不把未建联自动计为低价值，也不无限阻塞后续日记。后续修复关联可改变下一轮评分，不能回写已完成任务的保护快照。

同一任务重试复用已持久化快照，重复完成不再次冷却或强化。图在生成期间变化不使冻结名单漂移；来源内容改变或撤回则废弃该任务依据。日记记录完整来源签名，热冷状态不参与签名计算。新来源补入或来源正文变化导致修订，冷却本身不导致重写。

历史数据按可确定的来源映射节点，分批建立关联。无法确定完整回合的消息作为独立来源节点处理，不机械拼接。启用全局冷却前，先在固定真实语料上比较当前召回与新召回的证据覆盖、忠实度、重复率和成本，随后依据同一版本策略启用冷却；这属于实现内的验证步骤。

## 8. 首版实现状态

### 8.1 已接入的代码

- `memory/associations.py`：独立 SQLite 节点、理由、边、成员和事件表；原始回合及版本映射；双方原文片段与 scope 校验；独立来源去重；链 revision 失效后重算召回、引用强度。理由文本建立独立全文索引，权重不写正文 metadata。
- `memory/usage.py`：实际呈现与引用回执；按可信轮次与来源家族去重；核对来源版本、实际可见片段、最终回答和逐字原文。旧正文版本的使用记录不为新正文计分。
- `memory/retention.py`：持久化开始时的来源哈希、图水位、评分和保护名单；Top3/Top1；冷热系数及预算。维护只冷却热节点；冷节点只有实际引用后才进入重新评估，避免普通维护把每批冷来源全部复活。
- `service.py`、`worker.py`、`client.py`、`server.py`：新增 `associate` 任务和提交 RPC。状态更新优先；建联未就绪的巩固任务让出执行权且不消耗失败次数。失败达到上限后按已有图与先验继续；源内容改变则重新建立材料与快照。
- `retrieval.py`、`evidence.py`：最多两跳的 scope 内关联扩展、冷候选衰减、矛盾对照及方向限制；在 CrossEncoder 之后融合排名；来源家族去重。热原文进入直接索引和自动上下文，冷原文仍能作为证据回溯。
- 桌面、QQ、`MemoryJournal` 与提示词：本轮真实消息与引用的历史依赖分别记录，旧引文不被并入当前原始回合；完整回合跨记忆日边界不拆分；运行中回合有等待期限，超时后保留已有真实来源。提示预算内的资料先暂存，只有模型请求返回数据、且请求中确实含来源 ID 与片段时才确认呈现；`search_memory` 返回稳定 ID，`cite_memory` 暂存引用，结束时由服务核对。

旧库按每次维护最多 200 条记忆和 200 条消息分批回建节点；无效来源也登记已扫描标记，避免旧审计行阻塞后续数据。没有可信轮次的历史消息保留独立节点。保留策略不调用 `delete_memory()`，主库原文、日记完整来源和时态撤回继续分开管理。

## 9. 第二轮优化

本轮重点解决重复来源校验、候选证据重复生成，以及使用反馈不能区分关联理由的问题。

- 查询读取缓存只在单次请求内生效，以 SQLite `total_changes` 和 `data_version` 检测本连接及外部连接的变化；来源变化后重新读取，不使用跨轮旧证明。节点、来源消息、原文材料、链权重及证据来源遍历复用同一缓存；补齐按 memory_id 和 node_id 查找的索引。
- 原文证据在最终排序与来源家族去重后生成，只为实际选中的结果取证。冷摘要通过限定 scope 的原始来源读取证据，继续退出直接索引；撤回、删除和时态过滤保持优先。
- 引用回执可指定本轮实际呈现的 `chain_id`。唯一理由自动归属，多理由未归属的记录保留审计，不广播到所有链。单轮此前确认过的资料和理由不会因后续请求缩短而丢失；正文版本改变则重新确认。
- 旧计权策略缓存自动失效、按 `scoped-usage-v2` 重算，原始数据与使用事件不删除。最强理由评分只使用当前有效边；没有有效理由时用内容先验与真实使用作为后备。
- 建联查询使用真实正文，排除当前节点和同源派生材料，避免说话者编号等公共头部造成假候选。长材料保留与查询匹配的后段原文；零置信度、来源版本过时的关系不进入激活，失效成员不占用有效候选额度。

本轮完整回归共 294 项通过，其中关联测试 44 项；网关和经历协议测试 50 项通过。新增覆盖同连接修改、外部撤回、冷摘要取证、按理由独立引用、隐藏理由拒绝、长文尾部、旧关系失效与候选额度等边界。生产库仍只读，自动冷却仍关闭。优化前代码与同一语料的对比记录见 [优化验证报告](computer:///Users/bytedance/Bines/关联记忆优化验证-2026-10-24.md)。
