# 记忆服务报错修复与验证

日期：2026-11-13。范围：memory-worker、memory-server，以及连接两者的 ChatBot 网关。

## 结论

已确认、修复并部署导致 RPC 卡住的自主目标 SQL 全表扫描，以及网关丢失记忆连接异常类型、自动状态输出未先校验、建联核验输出缺少纠正机会。最终镜像 337 项回归通过，八个服务均健康，真实活动查询恢复为 66.66–164.78ms。异常时保留任务租约与提交回执，不重发不确定写入；模型错误最多纠正一次，未经核验的状态或关联不会提交。

服务长时间无响应已通过实时栈和真实 SQL 对照确认。历史退出 135 的原生崩溃原因仍未确认，不能将其解释为 OOM，也不能声称此类退出已根治。为两个记忆服务启用 `PYTHONFAULTHANDLER=1`，今后原生崩溃可输出线程栈。

## 已确认的根因与改动

核心阻塞来自 `LifeLedger._goals`：`activity_snapshot → life.snapshot → _goals` 在计算目标时，用 `le.source_ref='life:'||e.source_ref` 连接经历表。SQLite 不能使用经历主键，计划为 `SCAN e LEFT-JOIN`，随事件和经历数量增长重复扫描。正常的新经历会使目标缓存失效，反复触发这个慢查询，阻塞单线程 Memory Server，连带令 worker 领取/回执超时、网关堆积和管理页 503。

连接条件改为 `e.source_ref=substr(le.source_ref,6) AND substr(le.source_ref,1,5)='life:'`，以主键查找经历，保留严格的前缀、来源删除、scope 和时间过滤。未缩减目标历史或更改目标计算语义。

1. `MemoryUnavailable` 经网关变成 HTTP 503，再被 `GatewayClient` 统一转换为 `RuntimeError`。worker 因而将不确定的完成结果当成任务失败，调用 `fail_job`，重复告警也无法进入连接退避分支。网关现在返回明确错误类型；仅 `/memory` 的匹配响应还原为 `MemoryUnavailable`。业务校验失败和权限拒绝仍保留原有错误语义。
2. 自动状态模型可能复制当前状态字段或输出包装对象。原 worker 直接提交，server 才报“状态更新包含未知字段”。现在先校验提示词字段、文本类型与 `relationship_delta` 整数范围，保留单元素字符串数组兼容；不合格输出给模型一次具体纠正机会。提交异常不触发模型或 RPC 重放。
3. 紧凑建联草案已有有界纠正，但 `_verify_compact_association` 位于校验异常捕获范围外。第二次核验缺逗号或遗漏目标会直接失败。现在核验结果也进入同一纠正流程，两次不合格仍拒绝提交。证据编号、来源授权和事实核验未放宽。

## 运行证据与边界

- 原服务容器 `RestartCount=1`，历史退出 135；`OOMKilled=false`，cgroup `oom/oom_kill=0`。
- `/dev/shm` 总计 64MiB，使用约 4KiB；共享数据磁盘使用约 50%。这些值不支持 OOM 或共享内存耗尽结论。
- 故障期间 `ping` 3–10 秒超时，管理页 `/api/health` 返回 503。
- 13:12:29 第一次栈诊断重启后采样三次，服务线程均位于 `socket.poll`，该次没有抓到卡点；之后真实活动再次触发阻塞，才捕获到 `_goals` 热点。
- 重启后 `stats` 约 356ms，向量 `ready=true`、`pending_keys=0`、`quarantined_keys=0`。
- 隔离的领取路径三次合计约 0.39s，其中约 0.34s 是临时 HTTP 证据发送；此路径不是最终定位的阻塞源。
- 在线检索原本已使用 `repair_fts=rebuild`；全量 FTS 对比不支持“正常请求每次强制全量核验”的解释，未据此修改索引逻辑。
- 真实故障栈：`activity_snapshot → life.snapshot → _goals:583`，CPU 约 100%，向量 executor 空闲。利用已部署的 faulthandler，通过 SIGABRT **诱发采样**，容器仍 running、RestartCount=0；日志中的 `Fatal Python error: Aborted` 是诊断操作，不是一次自然崩溃。
- 旧目标 SQL 只读执行 2 秒仍未结束，仅遍历 716 行；新查询以 `sqlite_autoindex_experiences_1 (source_ref=?)` 查找，240.15ms 完整返回 5942 行。
- 新查询的完整 `_goals` 真实冷计算两次分别为 483.79ms、236.19ms，各返回 20 个目标。
